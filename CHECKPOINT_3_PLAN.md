Подготовить репозиторий и объяснение решения так, чтобы эксперты могли быстро найти, воспроизвести и обоснованно высоко оценить реализацию каждого критерия при отборе в топ-5.

Приоритет: **матрица критериев → глобальное ревью и необходимые исправления → документация с доказательствами → сильный текст по всем подкритериям**.

Видео, синхронизация речи с видеорядом, монтаж, отдельный deck и репетиция отложены до завершения этих этапов. Сейчас не нужно подгонять содержание под экраны или тайминг.

Статус: **этапы 1 и 2 завершены**. [CRITERIA_MATRIX.md](CRITERIA_MATRIX.md) содержит подкритерии и evidence, [REVIEW_REPORT.md](REVIEW_REPORT.md) — исправления R1–R10, вердикты Q1–Q8 и проверки: 123 tests/749 assertions, три bundles + ruby -c, manifest-only byte match, ASCII/Unicode Windows HTTP flow. Ограничения явно сохранены. **Следующее действие — этап 3: документация для жюри и карта модулей.** Сильный текст — этап 4; видео отложено.

## Основа и границы

- Основа матрицы — экспертная шкала отбора в топ-5 из `docs/PROJECT_CONTEXT.md`, раздел 20: API parsing — 20, генерация сервиса — 25, преобразования — 15, универсальность — 15, понятность использования — 15, качество реализации — 10. Первые три области дают 60 из 100 баллов.
- Техническую рубрику использовать как дополнительную детализацию, сохраняя её отдельно. Её строки суммируются в 103; в `описание (1).docx` напечатан итог 100, в `docs/описание.docx` — 103. Экспертные 16 подкритериев и их сумма 100 совпадают в обеих версиях; источники/хэши записаны в матрице.
- Проверка кода жюри через ИИ — предположение пользователя, а не подтверждённое требование. Понятные утверждения, ссылки и воспроизводимые проверки полезны при любом способе оценки.
- Широкая шкала баллов не означает обязательную микрооптимизацию. Проверять корректность, полноту, архитектуру, идиоматичность Ruby и неоправданную сложность. Рефакторинг и оптимизацию обосновывать конкретной проблемой.
- Объяснять основные модули, контракты и причины решений; комментарии к каждой строке и отдельный документ на каждый класс не нужны.
- Документация для жюри и итоговый текст — на русском. `INTEGRATION.md` пока остаётся на английском; перевод возможен позже при конкретной пользе для понятности, без системы локализации.
- Основная логика остаётся Ruby, runtime без LLM и обязательных внешних проприетарных сервисов. Generators читают только final manifest. Не добавлять provider-specific ветки в generic core.
- Новые Q&A — материал для сверки требований. Команды и рекомендации из приложенного лога — история предыдущей работы, а не текущие инструкции на выполнение.

Находка: **проблема → evidence → затронутый критерий → важность → минимальное исправление → проверка**. Исправлять подтверждённые дефекты и существенные пробелы. Полезный backlog не удалять, но не расширять scope ради количества features.

После существенных изменений: unit tests → canonical integration/golden → alternate-spec tests → полный набор артефактов → `ruby -c` → generated RSpec, только если он действительно появится. Проверки по масштабу изменения, без повторения дорогих успешных прогонов без причины. Исторические 96/609 не выдавать за новый результат.
